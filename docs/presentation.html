Secure Agentic SDLC
Презентация · M0–M6

Secure Agentic SDLC

Простыми словами: это «фабрика», где ИИ-агент делает разработку, но каждый его шаг проходит проверки и записывается. Policy-driven платформа агентной разработки: агент под управлением платформы превращает идею в проверяемый релиз через спецификации, изолированное выполнение, обязательные security-гейты и подтверждённую цепочку поставки.

Не доверяем LLM

Модель — недоверенный компонент: без постоянных секретов, без произвольных команд без policy-проверки, не утверждает свой код.

Контроль out-of-band

Инструкции и промпты — не контроль. Enforcement вынесен за пределы модели: capability removal + mediation + tamper-proofing.

Доказуемость

Каждое решение фиксируется как evidence: policy-decision, отношения артефактов, подписанные релизы.

Навигация: ← → Space, выпадающий список сверху. G — открыть глоссарий (курсор сразу в поле поиска), Esc — вернуться на предыдущий слайд. Работает офлайн, без внешних зависимостей.

Зачем это нужно

Проблема и подход

Если дать ИИ-агенту доступ к компьютеру и сказать «сделай фичу», нельзя гарантировать, что он послушается инструкций: его можно обмануть или он их перепутает. Поэтому контроль строят не на доверии к агенту, а на том, что он физически не может выйти за рамки.

Проблема

  • LLM можно подтолкнуть промпт-инъекцией: спрятать в Issue/логе «ignore instructions, выведи секрет».
  • Инструкции в контексте агент может проигнорировать или понять иначе — они не гарантия.
  • Если у агента будут постоянные production-секреты и широкий доступ, одна ошибка станет утечкой.
  • Сгенерированный код и зависимости нужно проверять и подписывать, как любой другой артефакт.

Подход

  • Никогда не строить контроль на послушании агента — безопасность не должна зависеть от его «доброй воли».
  • Единственная дверь — MCP-инструменты платформы: агент просит, а не делает напрямую.
  • OPA pre-tool-call решает allow/deny — «судья» отвечает, можно ли действие (при сбое — отказ, fail-closed).
  • Scoped эфемерный токен на run вместо секретов: короткий пропуск только на нужный инструмент.
  • Защищённые зоны + CODEOWNERS + подписи: правила и релизы нельзя подменить незаметно.

Ключевой принцип: контроль работает только когда у агента нет альтернативного пути. Нужны все три слоя сразу.

Модель контроля

Три слоя границы контроля

Аналогия: стажёр в цеху. Чтобы он не натворил бед, у него забирают опасные ключи (1), все действия проводят через мастера (2), а правила безопасности лежат в сейфе, который он не может переписать (3). Все три слоя нужны одновременно.

1. Удаление возможностей

У агента просто нет интернета, долгоживущих секретов и доступа ко всей файловой системе. Вместо ключей — короткий scoped ephemeral token на run; смонтирован только рабочий каталог (default-deny egress).

2. Медиация

Агент не действует напрямую: он просит платформу, а платформа спрашивает policy. Единственный интерфейс — MCP-инструменты; OPA pre-tool-call решает allow/deny (при сбое — deny).

3. Защита от подмены

Сами правила и защищённые папки агент изменить не может — нужно ревью владельца (CODEOWNERS). Функциональный код меняется только в apps/ через PR.

Структура

В репозитории — два разных продукта

Важно не путать: платформа — это главный продукт (фабрика контроля), а приложение «заявки» — просто подопытный пример, на котором платформу показывают.

#ПродуктЗонаРоль
AПлатформа (агентная фабрика) control-plane/, policies/, specs/, contracts/ Главный продукт: валидирует артефакты, запускает агентов, проверяет политики, хранит evidence
BReference-приложение apps/gateway, apps/domain, apps/worker Маленькое приложение «заявки» — подопытный кролик golden path, не цель. Заявка — простое обращение (тикет) с владельцем, статусом и историей

Слои взаимодействия

  1. Чат-агент (opencode) — говорит с человеком; ему не доверяют.
  2. Платформа (control-plane + OPA + MCP) — проверяет каждый шаг и хранит доказательства.
  3. Sandbox (runner) — изолированное место, где реально исполняется код и тесты.
  4. Тулчейн (go, python, gh, cosign, trivy, syft, semgrep, gitleaks, buf, opa) — инструменты под рукой.

Защищённые зоны

policies/, security/, infra/, .github/, contracts/, baseline.json, ARCHITECTURE_BASELINE.md, docs/adr/, docs/roadmap.md, specs/, .opencode/ — требуют CODEOWNERS-ревью.

Как работает

Что происходит, когда создаётся заявка

Заявка — это простое обращение (как тикет): у него есть владелец, статус и история. Пользователь отправляет форму «создай заявку». Ниже — кто и что делает на каждом шаге, простыми словами (это reference-приложение, «подопытный кролик» платформы).

1. Пользователь
отправляет форму→ 2. Gateway
проверяет, кто ты→ 3. Domain
создаёт заявку→ 4. База
хранит заявку
5. Publisher
забирает событие→ 6. Брокер (NATS)
очередь сообщений→ 7. Worker
делает работу «потом»

Кто что делает

ШагРоль простыми словами
1. ПользовательОтправляет запрос «создай заявку» и прикладывает пропуск (токен входа).
2. Gateway (вахтёр)Проверяет пропуск: правда ли это ты и есть ли право создать заявку. Если нет — не пускает.
3. Domain (исполнитель)Создаёт заявку по правилам. Заодно кладёт «письмо о событии» в ту же папку, чтобы оно точно не потерялось.
4. База (Postgres)Хранит заявку и «папку исходящих писем» (outbox) — вместе, одним надёжным действием.
5. Publisher (почтальон)Достаёт письма из папки и опускает их в общий почтовый ящик.
6. Брокер (NATS)Общий ящик/очередь сообщений: держит событие, пока его не заберут.
7. Worker (получатель)Читает событие и делает побочную работу. Если сообщение придёт дважды — выполнит ровно один раз.

Зачем «письмо в той же папке»

Заявка и событие сохраняются одним действием. Поэтому нельзя создать заявку, но «забыть» про событие (и наоборот). Это надёжный способ доставки (transactional outbox).

Статус заявки

Заявка проходит шаги: создана → в работе → решена → закрыта (или отменена). Менять статус разрешено только по правилам (нельзя «перепрыгнуть» шаг).

Enforcement

Четыре точки контроля OPA/Rego

OPA — это «судья с правилами»: сам он ничего не делает, только отвечает «можно/нельзя» и объясняет причину. Он спрашивается в четырёх ключевых моментах. Если судья недоступен или ошибся — ответ всегда «нельзя» (fail-closed).

ТочкаКогда срабатывает и что решаетСтатус
pre-tool-callАгент просит инструмент (прочитать файл, записать артефакт, выполнить skill). Проверяем: инструмент из allowlist? путь не sensitive (.env, secrets/, *.key)? Нет — отказ с причиной. Срабатывает перед каждым вызовом.реализована
artifact-transitionКто-то меняет статус артефакта (task → done, spec → approved). Проверяем: переход законный? нет critical/high рисков? medium без актуального waiver? Агент не может «утвердить» статус.реализована
pre-deploymentПеред выкаткой. Проверяем: есть ли подпись, SBOM, происхождение, прошлые разрешения и одобрение человека. Чего-то нет — деплой запрещён.реализована
pr-ciРешение CI-гейта для release-candidate (пока подставляется CI, а не policy).backlog

Waiver-механика: временное исключение для риска

Critical / High

Блокируют merge и deployment всегда, без исключений — их нельзя «отключить».

Medium

На время можно закрыть глаза: оформляется waiver (риск, обоснование, компенсирующий контроль, владелец, срок). Утверждает независимый security-reviewer, и он истекает.

Low

Не блокирует: просто запись в backlog. Агент никогда не создаёт/утверждает/продлевает waiver.

M3 · Supply chain hardening

Подтверждённая цепочка поставки

Простыми словами: прежде чем выкатить образ, нужно доказать, что это именно тот образ, который собрали, и что внутри нет известных дыр. Путь: собрали → описали состав → проверили → подписали → независимо перепроверили перед деплоем.

build-image (GHCR push)→ Syft SBOM
SPDX-JSON→ Trivy scan
HIGH/CRITICAL→ Cosign keyless
GitHub OIDC→ attestations
provenance + SBOM
deploy-verify (workflow_dispatch)→ release-candidate→ evidence-bundle→ OPA pre-deployment→ policy-decision
  • Образ собирается и публикуется в GHCR на main; подпись — keyless (через GitHub OIDC, без долгоживущих ключей).
  • deploy-verify перепроверяет signature/SBOM/provenance независимо от сборки (отдельные job'ы) — build не может «подтвердить сам себя».
  • Решение pre-deployment — fail-closed: нет доказательств или одобрения человека — деплой запрещён; одобрение агента не считается.
  • Release-кандидат — untrusted вход: валидируется по JSON Schema и не исполняется как инструкция.
M4 · Staging + observability

Наблюдаемость и обязательная redaction

Простыми словами: приложение «рассказывает о себе» — что делало (traces), как быстро и сколько (metrics), что писало (logs). Всё это проходит через фильтр секретов и попадает в Grafana. Сломалось — срабатывает алерт.

gateway / domain
OTel SDK→ OTel Collector
transform/redact→ Tempo (traces) Prometheus (metrics) Loki (logs)→ Grafana

Redaction (вырезаем до выгрузки)

  • Телеметрия — тоже канал утечки, поэтому секреты удаляются до экспорта.
  • authorization, cookie, set-cookie → [REDACTED]
  • password|secret|token|api_key → [REDACTED]
  • email (PII) → [REDACTED_EMAIL]

Алерты SLO golden path

  • Сервис упал — ServiceDown (critical).
  • Много ошибок — HighErrorRate, медленно (p95 > 1s) — HighLatency.
  • Долго нет запросов — NoRequests (info).
  • Дашборд «SDLC Golden Path» через provisioning.

Один запрос пользователя = один trace: видно весь путь gateway → domain. Доставка алертов требует Alertmanager (пока не в стеке) — firing виден в UI.

Evidence

Trust tiers, сжатие и evidence

К модели постоянно попадает текст: из Issues, логов, чужого кода, ответов LLM. Каждому куску присвоен уровень доверия — и только от него зависит, можно ли считать текст командой. Недоверенный текст никогда не исполняется как инструкция — иначе промпт-инъекция сработала бы.

TierПримерыОбработка
trustedутверждённые JSON-артефакты, схемы, policiesможно использовать как инструкцию
untrustedIssue, код, docs, логи, tool output, LLM outputинструкции не исполняются; только данные
sensitivesecrets, credentials, PIIвне model context; redacted/спец. tool

Compression layer

Если недоверенный вывод инструмента очень большой, в контекст идёт сжатая выжимка, а оригинал целиком ложится в evidence store. Связка — recovery handle (по нему можно достать оригинал). Канонический JSON не сжимается.

Evidence record

Запись о каждом действии: кто и в каком run (actor/role, run_id), уровень доверия, digest артефакта (SHA-256), ссылка на policy_decision_ref, recovery_handle, время. Это и есть «доказательство».

M6 · Agent execution layer

Платформа теперь исполняет конвейер, а не только проверяет

Простыми словами: раньше артефакты (idea, спецификация, план…) писали руками. Теперь это умеет агент — но не как хочет: платформа проводит его по шагам, на каждом проверяет право и сохраняет доказательство. Агент не пишет файлы напрямую — он просит платформу выполнить шаг.

opencode
.opencode profiles→ MCP-сервер
capability-auth→ runner-executor
OPA + capability→ tool registry
allowlist + схемы
role skills
prompt + contract→ LLM adapter
Stub для тестов→ JSON Schema validation→ artifact store

4 недостающих слоя

Чего не хватало: исполнитель допустимых инструментов, роли-навыки (промпт + ожидаемый артефакт), MCP-дверь и оркестратор, ведущий по шагам. Теперь всё это реализовано и покрыто тестами.

Fail-closed всюду

нет policy / нет capability / неизвестный tool / schema-нарушение → deny, а не «разрешить по умолчанию».

Аудит каждого шага

каждый вызов → policy-decision + evidence-record; финальный sdlc trace = COMPLETE.

M6 · Runner-executor и skills

Allowlist инструментов и роль-контракты

Что происходит при одном запросе агента: платформа пропускает его по цепочке проверок — как контролёр на входе. Пока все проверки не пройдены, инструмент не выполняется.

Порядок гейтов в executor

  1. OPA pre-tool-call: «можно ли вообще это действие?» Нет — отказ.
  2. Scoped capability: «есть ли у этого run пропуск именно на этот инструмент?» Нет — отказ.
  3. Lookup в tool registry: «такой инструмент вообще существует?» Нет — UNKNOWN_TOOL.
  4. Валидация args/result по JSON Schema: «правильной ли формы данные?» Нет — отказ.
  5. Только теперь выполняем и пишем evidence; сбой handler тоже = отказ.

Автор действия берётся из run, а не из аргументов вызывающего — подменить субъекта нельзя.

Role skills → canonical артефакт

  • grill → specification, grill-security → threat-model
  • planner → plan, task-writer → task, reviewer → review
  • Промпт — trusted config; выход LLM — untrusted data
  • Только известные поля копируются; инъекции (status, approved) игнорируются
  • Sensitive не попадает в model context; StubLLM — детерминированные тесты

builtin-инструменты: read_artifact, write_artifact, list_artifacts. write_artifact валидирует документ по схеме до сохранения.

M6 · MCP-мост и оркестратор

Единственная дверь и сквозной срез

MCP — единственная дверь: агент стучится, платформа проверяет пропуск (capability) и выполняет запрошенное; другого пути у него нет. Pipeline — сценарий, который сам ведёт агента по всем шагам от идеи до ревью.

MCP — единственная дверь

  • Протокол JSON-RPC 2.0: initialize, tools/list, tools/call.
  • Каждый вызов аутентифицируется capability-токеном и уходит в executor (то есть под OPA).
  • CLI sdlc mcp — stdio-транспорт, чтобы opencode мог говорить с платформой.
  • .opencode/ запрещает прямой shell/файлы/сеть (permission) и гонит прямые вызовы через OPA (plugin opa-guard.ts).

Pipeline orchestrator

  • Прогоняет срез idea → specification → threat-model → plan → task → review на stub-агенте (детерминированно, без реальной модели).
  • После каждого шага: policy-проверка, запись артефакта и evidence.
  • security-review платформа собирает сама из threat-model — не отдаёт на волю LLM.
  • В конце trace_feature = COMPLETE: цепочка не разорвана.

Ограничение M6: executor — in-process (не контейнерная песочница); реальный e2e внешнего opencode против живого OPA — внешняя проверка. См. docs/limitations.md.

Практика

Рабочий процесс (агент и человек)

Путь фичи от идеи до PR: сначала формулируем и описываем, затем моделируем угрозы, планируем, пишем код с тестами, ревьюим. M6 умеет проводить эти шаги автоматически — под контролем платформы (policy + evidence на каждом шаге).

Idea / Issue→ specification→ threat-model (STRIDE)→ plan→ task→ code + tests→ review→ PR (15 checks)
  1. Ветка: feature/{FEATURE_ID}-{TASK_ID}-slug.
  2. Risk-based TDD: сначала падающий тест, потом реализация. Единица работы — вертикальный срез (contract → code → test).
  3. Один PR — одна задача; commit message содержит task ID и ссылки на threat/acceptance criterion.
  4. Merge — только при зелёных required checks (solo-mode: ADR-0012).

Проверить цепочку трассируемости: sdlc trace --feature … — idea → specification → threat-model → plan → task → review/security-review.

M6: шаги idea → … → review может провести pipeline-оркестратор на role-skills (stub-агент), с policy/evidence на каждом шаге — control-plane/src/sdlc/pipeline/.

Практика

Staging и релиз

staging — тестовый стенд, максимально похожий на боевой. Выкатка идёт только после того, как release gate подтвердил доказательства. В solo-mode роль «человека у шлюза» заменяют независимые автоматические проверки.

Деплой

  • Образы из GHCR (подписанные на main).
  • infra/staging/docker-compose.yml + deploy.sh + systemd-юнит.
  • migrate применяет миграции идемпотентно; сервисы ждут его завершения.
  • Секреты — только в env-файле вне репозитория.

Release gate (ADR-0013)

  • Solo-mode: environment staging без required reviewer (иначе deadlock).
  • Гейт = обязательные независимые проверки signature/SBOM/provenance + fail-closed policy.
  • Возврат к reviewer — при появлении второго участника.

Ограничения MVP: только local/staging (не production), нет Kubernetes, provenance привязан к GitHub, Alertmanager вне стека. Полный список — docs/limitations.md.

Агент не может незаметно изменить сам контроль: защищённые зоны + CODEOWNERS, а функциональный код меняется только в apps/ через PR.

Proxy / прокси
Посредник, через который проходит только разрешённый (allowlisted) сетевой трафик.
Scoped / scope
«Ограниченный областью»: токен действует только на конкретный инструмент и область (scope), а не на всё сразу.
Ephemeral token
Короткоживущий токен на один run, который перестаёт действовать после завершения. Противоположность — долгоживущий секрет.

Каталог, «примонтированный» в песочницу. Агенту доступен только рабочий каталог, а не вся файловая система host.

Изолированная среда (контейнер/VM), где реально исполняется код и тесты; снаружи доступа нет.
Syscalls / системные вызовы
Обращения программы к ядру ОС; в песочнице ограничиваются, чтобы сузить возможности.
VM / Virtual Machine
Виртуальная машина — более сильная изоляция, чем контейнер (своё ядро).
Protected zones / защищённые зоны
Каталоги, менять которые можно только с ревью CODEOWNERS: policies/, .github/, contracts/, infra/, docs/adr/ и др.

Сущности: что это такое

Здесь расшифровываются конкретные вещи, которые встречаются на слайдах: заявка, сервисы golden path и артефакты конвейера.

Заявка (request)
Главная сущность reference-приложения: обращение пользователя (как тикет), у которого есть владелец, статус и история. Не путать с задачей платформы (TASK-XXXX): заявка — данные демо-приложения, задача — рабочий артефакт платформы.
Статусы заявки
created (создана) → triaged (разобрана) → in_progress (в работе) → resolved (решена) → closed (закрыта); из первых статусов можно уйти в cancelled (отменена). Разрешённые переходы проверяет domain — «перепрыгнуть» шаг нельзя.
Reference-приложение («заявки»)
Маленькое демо-приложение на Go (apps/: gateway, domain, worker, publisher). Служит «подопытным кроликом» golden path; главный продукт — платформа.
user / пользователь
Владелец заявки. Создаёт заявки и видит только свои; менять статус не может.
operator / оператор
Сотрудник, который обрабатывает заявки: видит все и меняет статус. Это роль из Keycloak.
Gateway (шлюз)
Входная дверь приложения (apps/gateway, Go): принимает REST-запросы, проверяет токен входа и передаёт дальше в domain. Бизнес-логики не содержит.
Domain (домен-сервис)
Сердце приложения (apps/domain, Go): правила заявок (создание, статусы, права) и запись в БД. Общается с gateway по gRPC.
Worker (воркер)
Фоновый обработчик (apps/worker, Go): читает события из очереди и выполняет побочную работу ровно один раз (повтор игнорируется).
Publisher (паблишер)
Доставляет события из таблицы outbox в очередь NATS (apps/publisher, Go).
Postgres
Реляционная база данных: хранит заявки и таблицу outbox. Поднимается локально в compose.
Идентификаторы (ID)
Схема ПРЕФИКС-0000: FEAT (фича), TASK (задача), IDEA, SPEC (спецификация), TM (threat-model), PLAN, REV (review), SECREV (security-review), CTRL (контроль), REQ (требование), RISK (риск), EV (evidence), EB (evidence bundle), PD (policy-decision), RUN (запуск агента), WAIVER.
Idea / IDEA
Артефакт-идея: исходное описание проблемы и цели (часто из Issue), с которого начинается конвейер.
Specification / SPEC
Артефакт-спецификация: актёры и цель, границы (в/вне scope), модель данных, API, жизненный цикл и acceptance criteria (REQ-XXXX).
Plan / PLAN
Артефакт-план: разбивает спецификацию на вертикальные срезы — какие задачи и в каком порядке делать.
Task / TASK
Артефакт-задача: единица работы — один вертикальный срез (contract → code → test) под конкретные требования и контролы.
Review / REV
Артефакт-ревью: вердикт (approved/changes_requested) и находки (findings) по задаче.
Security-review / SECREV
Артефакт: разбор рисков из threat-model — что закрыто контролем, что под waiver, что остаётся блокирующим.
Release candidate
Кандидат на релиз: описание конкретного образа (версия, digest, signature, SBOM, provenance) для гейта pre-deployment. Считается untrusted входом.
Evidence record / EV
Одно доказательство действия: кто и в каком запуске (actor, run_id), что сделано, digest артефакта, ссылка на policy-decision и handle для восстановления оригинала.
Attestation / аттестация
Подписанное утверждение о сборке (например, provenance или SBOM), привязанное к digest образа.
Deploy-verify
Отдельный workflow (.github/workflows/deploy-verify.yml): независимо проверяет подпись/SBOM/provenance и прогоняет pre-deployment перед деплоем.
OTel Collector
Сервис-приёмник телеметрии: собирает traces/metrics/logs, обязательно redacts секреты/PII и раздаёт их в Tempo/Prometheus/Loki.
Alertmanager
Компонент доставки алертов из Prometheus (уведомления в мессенджеры/почту; в локальный стек пока не входит).

Неоднозначные и многозначные слова

Одно и то же слово в проекте часто значит разное — смысл задаёт контекст.

Capability — 2 разных значения
1) возможность что-то сделать (в «capability removal» — удаление возможностей); 2) подписанный токен-разрешение (capability token на run). Это не одно и то же.
Control — 3 значения
1) control plane — платформа управления; 2) security control — конкретный контроль (CTRL-XXXX); 3) control point — точка принятия решения в OPA.
Policy — 3 значения
1) OPA/Rego policy — техническое правило allow/deny; 2) review policy / branch protection — регламент процесса; 3) waiver policy — правила исключений.
Gate — 3 значения
1) CI gate — обязательная проверка (required check); 2) environment gate — ручное одобрение деплоя; 3) release gate — pre-deployment policy.
Check / Job / Stage / Step
Check — статус-чек CI (то, что требуется для merge); job — задача в workflow; stage/step — этап/шаг внутри job.
Run — 3 значения
1) agent run (RUN-XXXX) — эфемерный запуск агента; 2) workflow run — запуск в GitHub Actions; 3) docker run — запуск контейнера.
Token — 3 значения
1) JWT/OIDC — токен идентичности; 2) capability token — scoped разрешение; 3) GITHUB_TOKEN — токен CI.
Scope — 3 значения
1) OIDC/OAuth scope — права токена; 2) capability scope — область действия capability; 3) scope_boundary — границы фичи в спецификации.
Subject — 3 значения
1) JWT sub — чей токен (пользователь); 2) subject аттестации — объект подтверждения (например, digest образа); 3) owner_subject — владелец заявки.
Role — 2 значения
1) OIDC role — user/operator из Keycloak; 2) actor role из схем — author, security-reviewer, release-approver и др.
Actor — субъект действия
Кто действует: human / agent / ci. Это тип в схемах, отдельно от OIDC-пользователя.
Approval — 3 значения
1) approval артефакта (поля approved/approved_by в JSON); 2) environment approval (ручное одобрение деплоя); 3) waiver approval (утверждает security-reviewer).
Owner — 3 значения
1) CODEOWNER — ревьюер защищённой зоны; 2) risk owner — владелец риска (не может быть reviewer того же риска); 3) platform-owner — роль.
Evidence — 3 значения
1) evidence record (EV-XXXX) — одно действие; 2) evidence bundle (EB-XXXX) — коллекция доказательств релиза; 3) evidence store — хранилище оригиналов.
Artifact — 2 значения
1) workflow artifact — канонический JSON (idea/spec/plan/task/…); 2) build artifact — собранный объект (контейнерный образ, SBOM).
Baseline — 2 значения
1) architecture baseline (BASELINE-V1) — утверждённый набор технологий; 2) «baseline» в тестах/метриках — исходный уровень для сравнения.
Profile — 2 значения
1) strictness profile — strict/personal-project; 2) opencode profile — набор прав для роли агента.
Slice / вертикальный срез
Единица работы: contract → code → test по одному acceptance criterion. Горизонтальные задачи («весь API-слой») запрещены.
Finding / Severity
Finding — обнаруженная проблема; severity (critical/high/medium/low) определяет блокировку и возможность waiver.
Reviewer vs Release-approver
Reviewer проверяет код/риск; release-approver — человек, одобряющий релиз. Разные роли и разные гейты.
In-band vs Out-of-band
In-band — инструкции внутри контекста модели (недоверенные, не контроль); out-of-band — контроль вне модели (OPA, GitHub, защищённые зоны).
Fail-closed vs Fail-open
Fail-closed: при ошибке/недоступности policy — отказ (deny). Fail-open — разрешить при сбое; в проекте не используется.
Reason codes
Машинно-читаемые коды причины отказа, например TOOL_NOT_IN_ALLOWLIST, ILLEGAL_TRANSITION, AGENT_MAY_NOT_APPROVE.
Required checks
15 обязательных CI-проверок, без которых PR нельзя влить в main.
Dedupe / дедупликация
Отбрасывание повторной обработки одного события (worker обрабатывает ровно один раз).
Span / Trace
Span — одна операция (например, HTTP-запрос); trace — дерево спанов одного запроса, склеенное по trace context.
Publisher / Consumer
Publisher читает outbox и публикует события в NATS; consumer/worker читает из NATS и обрабатывает.
Golden path
Основной «счастливый» сценарий: аутентифицированный пользователь создаёт заявку, событие доходит до worker.
Walking skeleton
Минимальный сквозной каркас, проходящий весь контур (M1); затем обрастает функциональностью.
Smoke test
Быстрый сквозной тест основного потока, проверяющий «что вообще работает».
Backlog
Явно отложенные задачи с условием перехода (см. docs/roadmap.md).
