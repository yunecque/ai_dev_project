# ADR-0011: Граница контроля (capability removal + mediation) и размещение IDE-агента

- **Статус:** accepted (размещение агента — M1 host, целевое — контейнер)
- **Дата:** 2026-09-22
- **Контекст:** LLM/IDE-агент — недоверенный компонент. Инструкции в его контексте (`AGENTS.md`,
  промпты, Issue, tool output) являются in-band и не могут служить контролем: их можно
  проигнорировать, переинтерпретировать или подменить промпт-инъекцией. При этом агент физически
  запускается рядом с проектом и имеет прямой доступ к сети, ФС и тулчейну. Нужно определить, где
  проходит граница принуждения и где именно исполняется агент.
- **Решение:**
  1. **Enforcement — только out-of-band.** Контроль никогда не строится на послушании модели.
  2. **Три обязательных слоя** границы:
     - *capability removal* — у агента нет прямого сетевого выхода (default-deny egress), нет
       долгоживущих секретов, только scoped ephemeral token на run, ограниченный mount ФС;
     - *mediation* — единственный интерфейс к внешнему миру — MCP-инструменты платформы; каждый
       вызов проходит OPA `pre-tool-call` (fail-closed, ADR-0004);
     - *tamper-proofing* — защищённые зоны (`policies/`, `.github/`, `contracts/`, `infra/`,
       `docs/adr/`, `baseline.json`) под CODEOWNERS; агент меняет только `apps/` через PR.
     Отсутствие любого слоя делает контроль декоративным.
  3. **Платформа заменяет агенту интернет**, а не фильтрует его: вместо неограниченного доступа —
     узкий набор политик-разрешённых инструментов.
  4. **Размещение IDE-агента:** M1 — opencode на Windows host (минимум трения); целевое —
     opencode внутри devcontainer/песочницы (нет доступа к host); промежуточное — WSL (паритет
     с CI). Sandbox (runner) — всегда эфемерный контейнер, независимо от размещения агента.
  5. **Ограничение opencode** — через `.opencode/`: MCP-сервер платформы, урезанный `permission`
     (MCP как единственная дверь), plugin-хук `tool.execute.before` / `permission.ask` к OPA.
     Роли из схем (`grill`, `grill-security`, `planner`, `implementer`, `reviewer`) отображаются
     на отдельные profiles прав.
- **Обоснование:** медиация без удаления альтернативных каналов не является контролем; агент может
  обойти «панель». Только сочетание удаления возможностей, медиации и защиты от подмены даёт
  проверяемую границу. В `strict`-профиле это обязательный минимум.
- **Последствия:**
  - runner и OPA-клиент обязаны реализовать scoped token и default-deny egress;
  - `pre-tool-call` становится обязательной точкой и для IDE-агента (через MCP/plugin), а не только
    для внутренних вызовов платформы;
  - agent profiles прав фиксируются в `.opencode/`;
  - M1 допускает работу агента на host с широкими правами — это явное отклонение режима
    «строим платформу», которое должно исчезнуть в режиме «платформа управляет проектом».
- **Открытый вопрос:** политика review в solo-mode (ADR появится после решения).
